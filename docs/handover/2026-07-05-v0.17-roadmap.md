## Global constraints (bind every workstream)

- **No framework, no build step, no new runtime deps.** Vanilla ESM (`"type": "module"`), Node
  built-ins, `ajv` only. Never add a dependency.
- **The three-layer write rule** (CLAUDE.md): commands = orchestration prose + atomic swap;
  deterministic Node (`scripts/`, `workflows/lib/`) = all validation/transforms/writes,
  unit-tested; LLM workflows (`workflows/internal/`) = creative prose only, never mutate the
  map, and must keep the defensive `JSON.parse`-a-stringified-`args` guard.
- **Pure-function + CLI split** for every new script: exported pure function (unit-tested) +
  thin CLI guarded by `if (process.argv[1] === fileURLToPath(import.meta.url))`.
- **Two write gates**: JSON Schema (`schemas/v1/`) + referential integrity
  (`checkReferentialIntegrity` in `scripts/validate-kartograph.js`). Any new map block gets
  both: schema validation AND an integrity check.
- **Slugs** `^[a-z0-9][a-z0-9-]*$` are the key space; scenario IDs are
  `<capabilitySlug>/<featureFile>#"<scenarioName>"`.
- **Maturity is derived, never declared.** Progress (tracking) never changes maturity.
- **No fallbacks to old paths.** When WS3 moves directories, old locations are dead (same
  policy as the earlier `.kartograph/` map move).
- **Tests gate the pure layer** (`node:test`). Every new pure function gets tests. Renderer
  DOM/CSS and command prose are verified by review + human GUI walkthrough, not unit tests.
- **Commit per workstream** (one or a few commits, conventional style `feat(...)`/`fix(...)`/
  `chore(...)`), each with `npm test` green first. Do not bump versions until WS13.
- **Never touch**: `.superpowers/`, anything under `docs/superpowers/` history, or the user's
  other projects.

## WS4 — `scenarioNotes` foundation

**Why:** WS5 (walk failures) and WS8 (build friction) need a durable, schema-gated place to
record *why a scenario is stuck*. Tracking state alone loses that context.

**Design (final):**
- New **optional** top-level map block `scenarioNotes`: object keyed by scenario ID (same key
  space as `tracking`), values `{ "reason": string (minLength 1), "date": "YYYY-MM-DD",
  "source": "walk" | "build" }`, `additionalProperties: false`.
- Lifecycle: a note is written when a scenario is set to `open` with a reason; it is
  **cleared** whenever the scenario is set to `developed` or `accepted`. Empty block is
  removed from the map (mirror `tracking`'s behavior).

**Do:**
1. Schema: extend `schemas/v1/` kartograph schema with `scenarioNotes` as above.
2. Pure helpers `workflows/lib/notes.js`: `getScenarioNote(map, id)`,
   `setScenarioNote(map, id, { reason, date, source })`, `clearScenarioNote(map, id)` —
   immutably returning new maps, mirroring `workflows/lib/tracking.js` style.
3. Integrity gate: in `checkReferentialIntegrity`, flag `scenarioNotes` entries whose
   capability slug no longer exists (mirror the existing `tracking` check).
4. `scripts/set-tracking.js`: accept optional `--reason "<text>"` and
   `--source walk|build` (default `walk`) when the new state is `open` → write the note
   (date = today, computed in the CLI wrapper, passed into the pure layer). Setting
   `developed`/`accepted` clears any note for that ID. Update the usage text.
5. Tests: `test/notes.test.js` (helpers incl. clear-on-advance + empty-block removal), schema
   acceptance/rejection cases, integrity-gate case, set-tracking flag behavior.

**Out of scope:** surfacing notes in the desktop UI (future).

## WS5 — `/karto-walk` acceptance command

**Why:** Accepted is the product's core claim and the only unsupported step.

**Do:**
1. New deterministic lister — pure fn + CLI `scripts/list-tracking.js <root> [state]`:
   walks the map + `features/` and prints JSON
   `[{ context, capability, feature, scenario, state, class, note? }]` filtered to `state`
   (default `developed`). Reuse `workflows/lib/feature-read.js` / `tracking.js` / `notes.js`.
   Unit-test the pure function.
2. New `commands/karto-walk.md` (register in `plugin.json` commands, mention in README):
   - **Scope** from `$ARGUMENTS`: empty = whole map; `context:<slug>`; or a capability slug.
   - Steps the command prescribes:
     a. Run `list-tracking.js . developed` (filter to scope). If empty: report "nothing to
        walk" and stop.
     b. Ask the user to start their app (suggest how, e.g. their run script); offer
        `/karto-show` for the map view. Do not manage the app lifecycle.
     c. **One scenario at a time**: show capability · feature · scenario name, then the
        Given/When/Then steps verbatim (plain language, no tech). Ask exactly:
        **Pass / Fail / Skip**.
        - Pass → `node ${CLAUDE_PLUGIN_ROOT}/scripts/set-tracking.js . <ctx> <cap> <feature> "<scenario>" accepted`
        - Fail → ask one short "what went wrong?", then
          `... "<scenario>" open --reason "<answer>" --source walk`
        - Skip → no write.
     d. Summary: counts accepted/failed/skipped; failed list with reasons; suggest
        `/karto-build <capability>` for capabilities with failures.
   - Tone rule: this is a walkthrough for a possibly non-technical person — the command must
     not paraphrase scenarios into tech-speak.

**Acceptance:** command follows the deterministic-writes convention (all state changes via
`set-tracking.js`); `plugin.json` updated; lister tested.

## WS6 — Re-walk candidates after build

**Why:** Building capability C can silently break Accepted behavior in capabilities that
depend on C. The map's dependency edges already carry the information.

**Do:**
1. **Verify edge semantics first** (read the schema/CLAUDE.md): dependencies are
   `{ from, to }` = "from depends on to". Candidates for rebuilt capability C = for each edge
   with `to === C`, the `from` capability's **Accepted** scenarios.
2. Pure helper `workflows/lib/rewalk.js`: `rewalkCandidates(map, builtCapability)` →
   `[{ capability, scenarioId }]` (parse tracking keys with the ids helpers). Unit tests
   (incl. no-edges and transitive NOT included — direct dependents only, v1).
3. CLI `scripts/rewalk-candidates.js <root> <capability>` printing JSON + a human line.
4. `commands/karto-build.md`: after the reconcile step, add: run `rewalk-candidates.js`; if
   non-empty, list them and suggest `/karto-walk <capability>` for each affected capability.

## WS7 — Revise flow

**Decision (final scope):** v1 supports **retire-scenario**, **retire-capability**, and
**display-name renames** (capability + context). **Non-goals (document them):** slug renames,
moving capabilities between contexts, merging/splitting capabilities.

**Do:**
1. **Discovery schema** (`schemas/v1/` discovery): optional `revisions` array; entries:
   - `{ "type": "retire-scenario", "capability": slug, "feature": "<file>.feature", "scenario": string, "reason": string }`
   - `{ "type": "retire-capability", "capability": slug, "reason": string }`
   - `{ "type": "rename-capability", "capability": slug, "newName": string, "reason": string }`
   - `{ "type": "rename-context", "context": slug, "newName": string, "reason": string }`
2. **Pure transforms:**
   - `workflows/lib/gherkin-edit.js`: `removeScenario(featureText, scenarioName)` → new text
     with that scenario block (its tags + steps) removed, preserving the rest byte-faithfully;
     returns `null`/throws if not found. Unit tests with tag lines, Background, last-scenario
     cases.
   - Extend `workflows/lib/apply-discovery.js` (or a sibling `apply-revisions.js` if cleaner —
     keep `applyDiscovery` pure either way): map-side effects of each revision type:
     retire-scenario → drop its `tracking` + `scenarioNotes` entries; retire-capability →
     delete the capability, drop all dependency edges touching it, drop its tracking/notes
     entries; renames → update `name` only. Unit tests per type incl. cascade cases.
3. **`/karto-chart` integration** (`commands/karto-chart.md`): when the survey has
   `revisions`: apply map-side transforms to the working copy (step 2 of the existing flow);
   for each retire-scenario also edit the `.feature` file via a small deterministic script
   (add `scripts/retire-scenario.js <root> <ctx> <cap> <feature> "<scenario>"` wrapping
   `gherkin-edit.js`); for retire-capability, after the atomic swap succeeds,
   `git rm -r features/<context>/<capability>/` and report it. Reconcile (existing step)
   recomputes maturity — retiring scenarios may lower maturity; that is correct.
4. **New `commands/karto-revise.md`** (register in `plugin.json`, mention in README):
   interactive, read-only like explore but focused on *existing* behavior: identify the
   target capability/scenarios from the map with the user, confirm each revision explicitly
   ("retire X because Y"), then assemble the survey JSON **in-session** (no LLM workflow
   needed — revisions are precise, not creative), validate with
   `validate-discovery.js`, save to `.kartograph/surveys/<date>-<slug>.discovery.json`
   (surveys may mix `revisions` with normal additive findings — a "change" is retire-old +
   add-new), render HTML, then hand off to `/karto-chart` exactly like explore does.

## WS8 — Spec-friction rule in build

**Do** (edits to `commands/karto-build.md` only):
1. In step 1 (find open scenarios): also read `scenarioNotes` for the capability (via
   `list-tracking.js` output) and treat prior walk-failures/frictions as context for the
   implementation.
2. New rule paragraph (place after the "Build the whole vertical slice" block):
   **Never edit a `.feature` file during build.** If a scenario cannot be implemented as
   written (ambiguous Then, impossible Given, contradicts another scenario), do not force it
   and do not rewrite it: skip it, record the friction —
   `set-tracking.js . <ctx> <cap> <feature> "<scenario>" open --reason "<friction>" --source build`
   — continue with the other scenarios, and in the final report list the frictions and point
   the user to `/karto-revise`. The map changes only through explore/revise → chart.
